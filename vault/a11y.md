# Latin in an English page

The UI is bilingual by design: the chrome speaks English, the words speak Latin. Two decisions fall out of that — how to *mark* the Latin, and what to do when a Latin word is the only label on a control.

## `lang="la"` on the Latin, not English `aria-label`s

Every run of Latin text carries `lang="la"`. The document root stays `lang="en"` (`src/routes/__root.tsx`).

The tempting alternative was to leave the Latin unmarked and hang an English `aria-label` on it — `aria-label="Search"` on *Quaere*. That is worse in three separate ways:

| | `lang="la"` | English `aria-label` |
| --- | --- | --- |
| The text itself | stays intact | replaced for AT users |
| WCAG 3.1.2 Language of Parts (AA) | satisfied | still failing |
| WCAG 2.5.3 Label in Name (A) | satisfied | **broken** |

The 2.5.3 break is the decisive one. The accessible name must *contain* the visible label, or a speech-input user who reads *Quaere* off the screen and says “click Quaere” hits nothing. Renaming the button out from under them is a regression dressed up as a fix.

And `aria-label` cannot solve the problem it was proposed for anyway: it is a flat string with no markup, so it inherits the language context of its element. There is no way to say “this label is Latin.”

What `lang` buys beyond conformance:

- translation tools leave it alone — Chrome stops offering to repair *Quaere* as mangled English
- `:lang(la)` becomes available as a styling hook
- correct hyphenation and font matching, which matters here: the `latin-ext` subset in `styles.css` is fetched only for macronned words

### It is usually silent, and that is fine

Most screen readers ship no Latin voice. NVDA with eSpeak has one; JAWS and VoiceOver generally fall back to the default voice and apply English rules anyway. So `lang="la"` often produces **no audible change at all**.

Do it regardless — it is a conformance requirement and a tooling hint, not a text-to-speech feature. Just do not expect to hear it working.

### Where it goes

On the smallest element that wraps the whole Latin run, and no smaller. The header logo first had `lang="la"` on two sibling spans, which left the space between *Dictionarium* and *Latinum* outside both. It now sits once on the `<Link>`.

Strictly, 3.1.2 exempts proper names, so the attribute on the site's own name is optional. Kept for consistency.

### The one place `lang` cannot reach

The header tooltip needs the label “What does *Verba sub manū* mean?” — mostly English, with Latin inside. An `aria-label` is a flat string and cannot express that, so the label became real hidden content instead:

```tsx
<span className="sr-only">
  What does <span lang="la">Verba sub manū</span> mean?
</span>
```

The rule that generalises: **when a label mixes languages, it has to be content, not an attribute.**

### Homoglyphs make the claim false

`dēlē` shipped briefly as `dе̄lе̄`, where both *e*s were U+0435 CYRILLIC SMALL LETTER IE carrying a combining macron. It rendered perfectly and looked correct in review.

`lang="la"` over Cyrillic text is a lie to assistive tech, and find-in-page and copy-paste break with it. So: macrons are always **precomposed Latin** — `ū` U+016B, `ē` U+0113, `ī` U+012B — never a base letter plus U+0304, and never a lookalike borrowed from another script.

This is enforced, by `scripts/check-macrons.ts` — wired into `npm run check`, or run alone:

```sh
npm run check:macrons
```

It scans `src/**/*.{ts,tsx}` for three things, and exits non-zero on any of them:

| Flagged | Range | Why |
| --- | --- | --- |
| combining marks | U+0300–U+036F | a macron that should be precomposed |
| Greek | U+0370–U+03FF | lookalike letters |
| Cyrillic | U+0400–U+04FF | lookalike letters |

Real macrons (`ē` U+0113) and ordinary typography (em dashes, curly quotes) pass untouched. Where text is merely decomposed rather than the wrong script, the output suggests the NFC form.

Not a Biome rule, and not for lack of trying. Biome’s GritQL plugins match JS *expressions*, so a pattern that catches a bad string literal misses the same characters sitting in JSX text — which is exactly where this bug lived. The supported subset also has no node-kind patterns, so a regex over a generic `$node` fires once per enclosing node: seven diagnostics for one word. A plain scan over the file text is the honest tool for what is really a text problem.

## English glosses on the Latin buttons

*Quaere* and *dēlē* are the only labels on their controls. Someone who does not read Latin is stuck — and that is equally true for sighted users, so this is a comprehension problem that happens to surface first in accessibility review, not a screen-reader problem.

The fix **appends**; it never replaces:

```tsx
<Button variant="primary" className="uppercase self-center" lang="la">
  Quaere
  <span className="sr-only" lang="en">{" (search)"}</span>
</Button>
```

| Visible | Accessible name |
| --- | --- |
| *Quaere* | Quaere (search) |
| *dēlē* | dēlē (clear) |

Three details are load-bearing:

- **Appending is what preserves 2.5.3.** The accessible name still contains the visible label, so “click Quaere” still works. Replacing it would reintroduce exactly the failure the `lang` decision avoided.
- **`lang="en"` on the inner span.** Without it the gloss inherits `lang="la"` from the button, and a reader with a Latin voice pronounces “search” as Latin. Every hidden gloss nested inside a `lang="la"` element has to switch back explicitly.
- **`{" (search)"}` rather than a bare leading space.** JSX strips whitespace at the start of a line, so a `<span> (search)</span>` broken across lines loses it and reads “Quaeresearch”.

Because `sr-only` is `position: absolute`, no gloss affects the flex layout, and `uppercase` on the parent never touches text that does not render.

Visible English subtitles were considered and rejected. The Latin labels are the point of the product; the gloss is a safety net, not a translation layer.
